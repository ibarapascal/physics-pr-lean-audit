## 0. Environment and general conventions

- Native environment: compute node A `env/pp3016` (`uv pip install pandapower@git+…@0c6a1f0a`, pandapower 3.4.0, numpy 2.3.5, scipy 1.16.3, pandas 2.3.3). **A native environment is available.** numba is not installed (affects speed only).
- Seed = 20261017 + 8×10 + track number; the random numbers of each point are `default_rng([seed, branch number, point number])`; the point parameters are drawn first and then evaluated; a rejected point is recomputed once with exactly the same parameters, and the bad check counts as a rejection only if it matches the observed value (otherwise it is counted as "non-replayable" and not as a rejection).
- Equal split over branches: N is split equally over the number of branches k (the remainder goes to the first branches), each branch gets at least ⌊N/k⌋. The discrete values stated explicitly in the plan are added as mandatory points (not counted in N), listed separately as `n_must` in the JSON.
- Verdict: if any check within a point exceeds its tolerance, the point is a rejection; if no tolerance is exceeded but an exception/NaN/non-convergence occurs, it is a failure (counted separately, not a violation).
- Tolerances: those written in the plan; when the plan gives only a relative tolerance the absolute term is 0; when the plan gives none, relative 1e-6 and absolute 1e-12 (protocol default). Complex values: the second and third tracks write "componentwise", so real and imaginary parts are judged separately; the first track does not say, so the complex modulus is used.
- The network is built once and then the tables are modified before each computation (`net.trafo.at[...]=`, `net.ext_grid.loc[...]=`): measured at ~58 ms per network build and ~7 ms per calc_sc (second-level probe on compute node A), so modifying tables is an order of magnitude faster than rebuilding. The third track's plan itself allows "public table assignments"; for the first and second tracks this is recorded as an implementation judgment.

## 6. Post-smoke corrections (2026-10-17, after the first smoke run with N=100; protocol §6 permits fixing script errors only)

First smoke output: compute node A `dq1/outputs/pp3016_t{1,2,3}.json`. For the first track only `ADD_pf3ph_Dyn` errored (25/25 failed, n_checks=0); the second track had 52/100 rejections. The diagnosis used only the smoke JSON, the library source (viewed read-only in compute node A `env/pp3016`), and recomputation of the sampled parameters from the seed (pure random numbers, no power flow run); the effect of the corrections is verified by the second smoke run, and was marked "speculation" before that.

- **S1 Track 1 additional check `t1_e_pf` (the whole function in `spotcheck.py`)**
  - Symptom: all 25 points raise `LoadflowNotConverged: Power Flow nr did not converge after 30 iterations!`, thrown from `runpp_3ph.py:646`: the outer sequence-component fixed-point iteration did not reach `outer_tolerance_mva=3e-8` (hard-coded, per unit, independent of `tolerance_mva`) in 30 iterations.
  - Cause: J7 takes the load as 0.01·S_T (1 kW–1 MW), single-phase on 0.4 kV; in the plan's domain R_N∈[0,1000] Ω the single-phase load circuit must go through the neutral, and the circuit can deliver at most about V_ph²/(4|Z_N|) (about 13 W at 1000 Ω). Recomputing these 25 points from the seed: the load is 116–70 800 times the maximum deliverable power, so there is physically no solution and the power flow necessarily fails to converge. In addition, the 1e-8 Ω positive sequence of the external line in J8 makes the admittance more than ten orders of magnitude larger than the load, and `tolerance_mva=1e-10` is below the mismatch floor attainable in double precision (speculation), so convergence also fails for small loads.
