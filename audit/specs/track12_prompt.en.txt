You are the "invariant writer" for an audit of physics software (one of two independent tracks; the other track cannot see you, and you may not look at it). For 12 GitHub PRs that have been merged into physics/engineering simulation libraries, write for each one: the library-level invariants this change **should satisfy** physically, and how to check them numerically through the merged public API. The purpose is to test later, by random spot checks and formal proofs, whether these changes are physically right.

## Input and output
- Input: `<workdir>` (repo, number, url).
- Output: `invariants.md` in the same directory, one section per PR, following the template below; write each one to disk as soon as it is finished.
- **Independence rule**: read only this csv and GitHub (the PR page, the diff, the source at the merge commit, PR/issue discussion, the cited literature). Do not read any file under `<private directory>`, and do not read any directory in the scratchpad other than `a1inv/w1/`.

## Template for each PR
```
## <repo>#<number> <title>
- What changed (1–3 sentences, naming files and formulas):
- Invariants (mathematical statements; write them as checkable equalities/inequalities, give variables, sign conventions, domain of validity):
- Sources of the invariants (first principles / literature formula / consistency with other implementations in the library / dimensions):
- Common operating domain (range of each input, with the basis):
- Numerical check method (which public API of the merge commit, what to compute, what to compare against, suggested tolerance and why; if finite differences are needed, the step-size strategy):
- Do the PR's own tests already check this invariant (yes/partial/no, naming test files and assertions):
- Do you expect the change to satisfy it (satisfies / may not satisfy / uncertain), with one or two sentences of reasoning (speculation, not a conclusion):
- Environment: merge commit SHA, language and dependencies needed, estimated setup difficulty (low/medium/high):
- Formalization (Lean) feasibility: can the invariant be written as a proposition over finite-dimensional reals, and what are the main obstacles:
```
- The invariants should target **the physics this change touches**; prefer narrow and checkable over a generic "energy is conserved". If a PR has several relevant invariants, list the most important 1–3 and mark which are primary and which secondary.
- If you think no numerically checkable invariant can be written for a change, say why; do not force one.
